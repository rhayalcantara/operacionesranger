## Problemas Encontrados y Soluciones

### No hubo problemas significativos

La implementación se realizó sin problemas. El script siguió el patrón de `seed-feriados.ts` y utilizó servicios existentes (`hashPasswordSync()`, `getTurnosPool()`, `closeConnections()`).

### Decisiones Menores

**Decisión 1: Usar hashPasswordSync() en vez de hashPassword()**

**Razón**:
- Scripts de seed son síncronos por naturaleza
- Solo 3 usuarios (carga mínima)
- Simplifica código (no necesita async/await)
- `hashPasswordSync()` está disponible en password.service.ts

**Alternativa**: Usar async/await con hashPassword() (más complejo, sin beneficio)

**Decisión 2: INSERT IGNORE en vez de verificar primero**

**Razón**:
- Más eficiente (1 query en vez de 2)
- Evita race conditions
- Patrón usado en seed-feriados.ts

**Resultado**: Implementado correctamente

---

## Decisiones Técnicas Tomadas

### 1. Uso de hashPasswordSync()

**Decisión**: Usar función síncrona de hashing en vez de asíncrona

**Justificación**:
- Scripts de seed no son servidores HTTP (bloqueo aceptable)
- Solo 3 usuarios (carga mínima, ~30ms por hash)
- Simplifica código significativamente
- `hashPasswordSync()` ya existe en password.service.ts

**Trade-off**: Bloquea event loop brevemente (aceptable en scripts)

### 2. INSERT IGNORE para duplicados

**Decisión**: Usar `INSERT IGNORE` en vez de SELECT + INSERT

**Justificación**:
- Más eficiente (1 query en vez de 2)
- Evita race conditions (aunque no hay concurrencia en scripts)
- Patrón consistente con seed-feriados.ts
- Más simple de implementar

**Trade-off**: No distingue entre diferentes errores de inserción (solo importa duplicados)

### 3. Opción --force elimina solo usuarios específicos

**Decisión**: DELETE solo afecta a usuarios con usernames específicos

**Justificación**:
- No elimina usuarios creados manualmente
- Seguro para BD con usuarios mixtos
- Predecible y controlado

**SQL**:
```sql
DELETE FROM sys_usuarios WHERE username IN ('admin', 'supervisor', 'consulta')
```

**Alternativa rechazada**: Eliminar TODOS los usuarios (demasiado destructivo)

### 4. Validación estricta de NODE_ENV

**Decisión**: Bloquear completamente ejecución en production

**Justificación**:
- Passwords de prueba NO deben usarse en producción
- Previene errores humanos
- Fácil de bypass si realmente se necesita (cambiar .env temporalmente)

**Mensaje de error**: Claro y con alternativas (usar endpoint POST /api/usuarios)
