**Estructura de la tabla**:

```sql
CREATE TABLE sys_auditoria (
  id INT AUTO_INCREMENT PRIMARY KEY,
  user_id INT NOT NULL,                            -- FK a sys_usuarios
  accion ENUM('CREATE', 'UPDATE', 'DELETE') NOT NULL,
  entidad VARCHAR(100) NOT NULL,                   -- Nombre de la tabla/recurso
  entidad_id INT NULL,                             -- ID del registro afectado
  ip_address VARCHAR(45) NULL,                     -- IP del cliente (IPv4/IPv6)
  datos_anteriores JSON NULL,                      -- Datos antes del cambio (UPDATE/DELETE)
  datos_nuevos JSON NULL,                          -- Datos después del cambio (CREATE/UPDATE)
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

  FOREIGN KEY (user_id) REFERENCES sys_usuarios(id_usuario)
    ON DELETE CASCADE ON UPDATE CASCADE
);
```

- `idx_user_entidad` - Búsquedas combinadas user+entidad

### 4. ✅ Implementar middleware de auditoría

**Archivo creado**: `backend/src/middlewares/audit.middleware.ts` (316 líneas)

**Funcionalidad principal**:

**Función factory**:
```typescript
export function auditMiddleware(entidad: string) {
  return async (req: Request, res: Response, next: NextFunction) => {
    // Middleware asíncrono que registra operaciones
  };
}
```

**Flujo de ejecución**:
1. Verificar si auditoría está habilitada (`env.audit.enabled`)
2. Verificar si usuario está autenticado (`req.user`)
3. Determinar acción (POST → CREATE, PUT → UPDATE, DELETE → DELETE)
4. Si GET u otro método, skip (solo auditar escritura)
5. Para UPDATE/DELETE: buscar datos anteriores ANTES de la operación
6. Interceptar `res.json()` para capturar respuesta
7. Extraer `entidad_id` de params, body o response
8. Construir objeto de auditoría con todos los datos
9. Insertar asíncronamente en `sys_auditoria` (fire-and-forget)
10. Enviar respuesta original al cliente

**Funciones auxiliares exportadas**:

- `sanitizeAuditData(data)` - Remueve campos sensibles antes de guardar
- `getAuditAction(method)` - Convierte HTTP method a acción (CREATE/UPDATE/DELETE)
- `getClientIp(req)` - Extrae IP del cliente (soporta proxies: x-forwarded-for, x-real-ip)
- `getEntityId(req, res)` - Extrae ID del registro de params, body o res.locals
- `fetchPreviousData(entidad, entidad_id)` - Obtiene datos anteriores para UPDATE/DELETE
- `insertAuditRecord(data)` - Inserta registro en sys_auditoria

**Características importantes**:

**Non-blocking**: El insert de auditoría es asíncrono (fire-and-forget), no bloquea el response al cliente.

**Fault-tolerant**: Si falla el insert de auditoría, el request continúa normalmente (se loguea el error con logger).

**Sanitización automática**: Campos sensibles (passwords, tokens) se remueven antes de guardar en BD.

**Captura completa**:
- CREATE: Solo `datos_nuevos`
- UPDATE: `datos_anteriores` + `datos_nuevos`
- DELETE: Solo `datos_anteriores`

**Captura de IP**: Soporta proxies y balanceadores de carga (x-forwarded-for, x-real-ip).

**Ejemplo de aplicación**:
```typescript
router.post('/', authMiddleware, requireRole('ADMIN'), auditMiddleware('clientes'), createController);
router.put('/:id', authMiddleware, requireRole('ADMIN'), auditMiddleware('clientes'), updateController);
router.delete('/:id', authMiddleware, requireRole('ADMIN'), auditMiddleware('clientes'), deleteController);
```

```typescript
  const url = req.originalUrl || req.url;
  const ip = req.ip || req.socket.remoteAddress;

  // Reemplazado console.error con logger.error

    url,

    name: error.name,
    code: error.code,
    statusCode: error.statusCode,
    // Stack trace solo en development
    stack: process.env.NODE_ENV === 'development' ? error.stack : undefined
  });
}
```

## Problemas Encontrados y Soluciones

### Problema 1: Foreign Key Error en sys_auditoria
**Descripción**: Al crear la tabla sys_auditoria, la FK a sys_usuarios falló porque usé `id` en lugar de `id_usuario`.

**Causa**: La tabla sys_usuarios usa `id_usuario` como PK, no `id`.

**Solución**: Verificar estructura de sys_usuarios con `DESCRIBE sys_usuarios;` y corregir FK:
```sql
FOREIGN KEY (user_id) REFERENCES sys_usuarios(id_usuario)
```

**Tiempo invertido**: 10 minutos

---

### Problema 2: Variables de entorno en env.ts y logger.ts
**Descripción**: El logger.ts intentaba acceder a `env.LOG_LEVEL` y `env.NODE_ENV` directamente, pero la estructura de `env` es diferente.

**Causa**: La estructura de `EnvConfig` anida las variables en objetos (`env.server.logLevel`, no `env.LOG_LEVEL`).

## Decisiones Técnicas Tomadas

### Decisión 1: Usar Winston en lugar de Pino
**Razón**:
- Winston tiene más plugins y transports disponibles
- Sintaxis más familiar para equipos JavaScript
- Comunidad más grande y documentación más extensa
- winston-daily-rotate-file es muy robusto

**Alternativa considerada**: Pino (más rápido, formato ndjson)

**Resultado**: Winston elegido, implementado exitosamente

---

### Decisión 2: Fire-and-forget para audit inserts
**Razón**:
- La auditoría no debe bloquear el response al cliente
- Si falla el insert de auditoría, el request debe continuar
- Performance: no agregar latencia a operaciones CRUD

**Implementación**:
```typescript
// Fire and forget (don't block response)
insertAuditRecord(auditData).catch((error) => {
  logger.error('Async audit insert failed', { error: error.message });
});
```

**Resultado**: Auditoría non-blocking, fault-tolerant

---

### Decisión 3: Interceptar res.json() en lugar de usar afterware
**Razón**:
- Express no tiene concepto de "afterware" oficial
- Interceptar res.json() permite capturar la respuesta antes de enviarla
- Permite extraer entity_id de la respuesta (ej: CREATE retorna { id: 123 })

**Alternativa considerada**: Usar Response.on('finish') event

**Resultado**: Intercepción de res.json() funciona perfectamente

---

### Decisión 4: Tabla JSON para datos_anteriores y datos_nuevos
**Razón**:
- Flexibilidad: puede almacenar cualquier estructura de datos
- Queries SQL nativas: MySQL 8.0 tiene funciones JSON robustas
- Tamaño variable: no desperdiciar espacio para registros pequeños

**Alternativa considerada**: Columna TEXT con JSON serializado como string

**Resultado**: Columna JSON nativa de MySQL

---

### Decisión 5: Sanitizar passwords/tokens antes de guardar en auditoría
**Razón**:
- Seguridad: nunca almacenar passwords en plaintext en ninguna tabla
- Cumplimiento: GDPR, PCI-DSS requieren protección de datos sensibles
- Mejor prevenir que curar: sanitizar automáticamente en middleware

**Implementación**: Función `sanitizeAuditData()` remueve campos sensibles recursivamente

**Resultado**: Auditoría segura, no expone información sensible

## Notas Adicionales

### Diferencia entre sys_auditoria y sys_auditoria_auth

**sys_auditoria_auth** (ya existía):
- Auditoría específica de **autenticación**
- Registra: login, logout, refresh token, cambio de password
- Campos: user_id, accion, ip_address, user_agent, exito, created_at

**sys_auditoria** (nueva, implementada en esta tarea):
- Auditoría **general** de operaciones CRUD
- Registra: CREATE, UPDATE, DELETE en todas las entidades
- Campos: user_id, accion, entidad, entidad_id, ip_address, datos_anteriores, datos_nuevos, created_at

**Justificación de separación**:
- **Propósitos diferentes**: Autenticación vs operaciones de datos
- **Consultas diferentes**: Análisis de sesiones vs trazabilidad de cambios
- **Retención diferente**: Auditoría de auth puede requerir más tiempo de retención por seguridad
