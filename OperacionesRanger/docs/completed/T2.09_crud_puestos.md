## Resumen

Se implementó exitosamente el CRUD completo para la gestión de puestos de seguridad (estaciones donde se asignan guardianes). ### 3. ✓ Crear servicio de Puestos con 6 métodos (puestos.service.ts)

**Archivo creado**: `backend/src/services/puestos.service.ts`

**Métodos implementados**:

**1. `getPuestos(filters)`**: Listar puestos paginados con filtros
- Filtros: page, pageSize, search, ubicacion_id, cliente_id, activo
- JOINs: ubicaciones + clientes
- Búsqueda: nombre LIKE, codigo LIKE, descripcion LIKE
- Response: `{ data: Puesto[], total: number }`

**2. `getPuestoById(id)`**: Obtener puesto por ID con relaciones
- JOINs: ubicaciones + clientes
- Incluye: cliente_nombre, ubicacion_nombre, turnos_count (0 por ahora)
- Response: `PuestoConRelaciones | null`

**3. `getTurnosByPuesto(puestoId, filters)`**: Turnos del puesto (preparado)
- Verificación: puesto existe
- **NOTA**: Tabla turnos NO existe, retorna `{ data: [], total: 0 }`
- Código preparado comentado para futura implementación

**4. `createPuesto(data)`**: Crear nuevo puesto
- Validaciones:
  - ubicacion_id existe y activo
  - codigo único dentro de ubicación (UK compuesto)
  - codigo normalizado a mayúsculas
- INSERT con defaults: activo = true
- Response: Puesto creado con relaciones (JOIN)

**5. `updatePuesto(id, data)`**: Actualizar puesto
- Validaciones:
  - Puesto existe
  - Si actualiza codigo, verificar unicidad en ubicación
- UPDATE dinámico (solo campos proporcionados)
- Response: Puesto actualizado con relaciones

**6. `deletePuesto(id)`**: Soft delete
- Validaciones:
  - Puesto existe
  - NO tiene turnos registrados (preparado para validación futura)
- Soft delete: `activo = false`
- Response: `{ message: "Puesto desactivado", id }`

**Funciones auxiliares**:
- `puestoExists()`: Verifica existencia
- `codigoExistsInUbicacion()`: Verifica código único
- `countPuestosByUbicacion()`: Cuenta puestos por ubicación

**Resultado**: Servicio completo con toda la lógica de negocio

## Decisiones Técnicas Tomadas

### 1. Preparación para tabla turnos
**Decisión**: Retornar array vacío en GET /api/puestos/:id/turnos pero con código comentado preparado
**Justificación**: La tabla `turnos` no existe aún (se implementará en futuras tareas), pero el endpoint está preparado para cuando se agregue

### 2. Soft delete en lugar de hard delete
**Decisión**: UPDATE `activo = false` en lugar de DELETE físico
**Justificación**: Mantener histórico y evitar problemas de integridad referencial cuando existan turnos

### 3. Normalización automática de código
**Decisión**: Transformar código a mayúsculas en schema Zod
**Justificación**: Consistencia de datos y facilitar búsquedas case-insensitive

### 4. Campos adicionales en modelo
**Decisión**: Agregar helpers `getTipoCobertura()`, `requiereCobertura24x7()`
**Justificación**: Facilitar lógica de negocio en frontend y reportes

### 5. Constraint único compuesto
**Decisión**: Validar código único dentro de ubicación en service (además de constraint DB)
**Justificación**: Proveer mensajes de error claros al usuario antes de violación de constraint
