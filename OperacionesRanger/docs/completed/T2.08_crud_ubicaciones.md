## Resumen

Se implementó exitosamente el CRUD completo para la entidad **Ubicaciones** del sistema de gestión de turnos. Las ubicaciones representan sitios físicos donde los clientes requieren servicios de seguridad (guardianes).

La implementación incluye:
- 5 endpoints REST completos (GET list, GET by ID, POST, PUT, DELETE)
- Validación completa con Zod schemas (incluyendo coordenadas GPS)
- Lógica de negocio robusta con validaciones de FK y reglas de negocio
- Control de acceso basado en roles (ADMIN, SUPERVISOR, CONSULTA)
- Suite de tests de integración con 30+ casos de prueba

**Características destacadas**:
- Validación de coordenadas GPS con formato "latitud,longitud" y rangos válidos
- Validación de cliente activo antes de crear ubicación
- Código único por cliente (UK compuesto: cliente_id + codigo)
- Protección contra eliminación si tiene puestos activos
- JOIN con tabla clientes y COUNT de puestos en GET by ID
- Filtrado por cliente_id en listado paginado

### [✓] 3. Crear servicio ubicaciones.service.ts

**Archivo**: `backend/src/services/ubicaciones.service.ts`
**Líneas**: 420

**Funciones públicas**:

1. **getUbicaciones(page, pageSize, search?, cliente_id?)**:
   - Paginación server-side
   - Búsqueda por nombre, dirección, provincia, municipio
   - Filtro opcional por cliente_id
   - Retorna: `{ data, total, page, pageSize, totalPages }`

2. **getUbicacionById(id)**:
   - JOIN con tabla `clientes` para obtener `cliente_nombre`
   - COUNT de puestos activos (`puestos_count`)
   - Throws error si no existe

3. **createUbicacion(dto)**:
   - Valida cliente existe y activo
   - Valida código único dentro del cliente
   - Parsea coordenadas GPS (si se proporcionan)
   - INSERT con valores transformados
   - Retorna ubicación creada

4. **updateUbicacion(id, dto)**:
   - Verifica ubicación existe
   - Si se cambia código, valida unicidad
   - UPDATE dinámico solo con campos proporcionados
   - Retorna ubicación actualizada

5. **deleteUbicacion(id)**:
   - Verifica ubicación existe
   - Valida que NO tenga puestos activos
   - Soft delete: `SET activo = FALSE`
   - Throws error descriptivo si tiene puestos activos

**Funciones auxiliares privadas**:

- `_codigoUnicoEnCliente(cliente_id, codigo, excludeId?)`: Valida UK

### Problema 2: Validación de Coordenadas GPS

**Descripción**: Decidir cómo almacenar y validar coordenadas GPS (objeto vs string).

**Decisión tomada**:
- **Frontend envía**: String "latitud,longitud" (ej: "18.486058,-69.931212")
- **Backend almacena**: Campos separados `latitud` (DECIMAL 10,8), `longitud` (DECIMAL 11,8)
- **Validación**: Schema Zod con regex + refine para rangos

**Justificación**:
- String es más fácil de copiar/pegar desde Google Maps
- Almacenamiento separado permite queries SQL geoespaciales futuras
- Validación de rangos protege contra datos incorrectos

**Tiempo invertido**: 15 minutos (diseño)

---

### Problema 3: Código Único por Cliente vs Global

**Descripción**: Constraint UK compuesto `(cliente_id, codigo)` permite mismos códigos en diferentes clientes.

**Decisión tomada**:
- Mantener UK compuesto (código único POR cliente, no global)
- Validar explícitamente en servicio antes de INSERT/UPDATE
- Mensaje de error claro: "El código XXX ya existe para este cliente"

**Justificación**:
- Diferentes clientes pueden querer usar mismos códigos (ej: "SEDE-01")
- Flexibilidad para naming conventions por cliente
- UK en BD previene race conditions

**Tiempo invertido**: 10 minutos (decisión)

## Decisiones Técnicas Tomadas

### 1. Parseo de Coordenadas GPS

**Decisión**: Crear helper `parseCoordenadasGPS()` que parsea y valida en un solo paso.

**Alternativas consideradas**:
- Validar solo en schema Zod (sin helper)
- Parsear en controlador

**Justificación**: Helper reutilizable, separa validación de parseo, facilita testing.

---

### 2. Soft Delete vs Hard Delete

**Decisión**: Implementar soft delete (`activo = false`) con validación de puestos activos.

**Justificación**:
- Mantiene integridad referencial
- Preserva historial
- Permite restauración

---

### 3. Filtro Cliente ID Opcional

**Decisión**: Usar construcción SQL condicional con WHERE clause dinámico.

**Implementación**:
```typescript
if (cliente_id !== undefined) {
  whereConditions.push('u.cliente_id = ?');
  queryParams.push(cliente_id);
}
```

**Justificación**: Más eficiente que `WHERE (:cliente_id IS NULL OR ...)` para MySQL optimizer.
