## Endpoints Implementados

### 1. GET /api/usuarios
- **Permisos**: ADMIN
- **Query params**: `page`, `pageSize`, `search`
- **Funcionalidad**: Lista paginada con búsqueda por username, email, nombre_completo
- **Response**: `{ data: UserSafeDTO[], total, page, pageSize, totalPages }`

### 2. GET /api/usuarios/:id
- **Permisos**: ADMIN
- **Path params**: `id` (número entero positivo)
- **Funcionalidad**: Obtiene usuario específico sin password_hash
- **Response**: `UserSafeDTO`

### 3. POST /api/usuarios
- **Permisos**: ADMIN
- **Body**: `{ username, password, email?, nombre_completo, rol }`
- **Validaciones**: Username único, email único, password fuerte (min 8 chars, mayúscula, minúscula, número)
- **Funcionalidad**: Crea nuevo usuario con password hasheado (bcrypt 10 rounds)
- **Response**: `UserSafeDTO` (201)

### 4. PUT /api/usuarios/:id
- **Permisos**: ADMIN
- **Body**: `{ email?, nombre_completo?, rol?, activo? }` (al menos uno)
- **Funcionalidad**: Actualiza campos permitidos (NO password)
- **Response**: `UserSafeDTO` (200)

### 5. DELETE /api/usuarios/:id
- **Permisos**: ADMIN
- **Funcionalidad**: Soft delete (activo = false), valida que no sea último admin
- **Response**: `{ message: "Usuario desactivado exitosamente" }` (200)

### 6. POST /api/usuarios/:id/reset-password
- **Permisos**: ADMIN
- **Funcionalidad**: Genera password temporal aleatorio de 12 caracteres (criptográficamente seguro)
- **Response**: `{ message, temporaryPassword, warning }` (200)

## Decisiones Técnicas Tomadas

### 1. Generación de Password Temporal

**Decisión**: Usar `crypto.randomBytes()` con 12 caracteres

**Justificación**:
- Criptográficamente seguro (no usar `Math.random()`)
- 12 caracteres = balance entre seguridad y usabilidad
- Mezcla de tipos de caracteres (mayúsculas, minúsculas, números, símbolos)

**Alternativas consideradas**:
- Generadores de passwords de librerías externas (rechazado: dependencia innecesaria)
- UUIDs (rechazado: muy largos y difíciles de tipear)

### 2. Soft Delete vs Hard Delete

**Decisión**: Implementar soft delete (activo = false)

**Justificación**:
- Preservar auditoría de creación/modificación (created_by, modified_by)
- Permitir reactivación si se elimina por error
- Mantener integridad referencial en otras tablas

**Trade-off**: Usuarios inactivos ocupan espacio en BD (aceptable)

### 3. Paginación Server-Side

**Decisión**: LIMIT y OFFSET en SQL, pageSize máximo 100

**Justificación**:
- Reducir carga de red (no enviar miles de registros)
- Performance: solo queries necesarios
- UX: carga incremental más rápida

**Configuración**: Default page=1, pageSize=20

### 4. No Permitir Cambio de Password en PUT

**Decisión**: Password solo se cambia con endpoint específico de reset

**Justificación**:
- Seguridad: reset requiere generación de password temporal
- Auditoría: cambios de password son eventos críticos
- UX: flujo separado es más claro

**Alternativa**: Incluir campo `password` opcional en UPDATE (rechazado)
