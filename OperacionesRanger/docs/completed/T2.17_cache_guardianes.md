## Resumen

Se ha implementado exitosamente un sistema de caché en memoria usando `node-cache` para optimizar las consultas de guardianes activos a la base de datos RRHH externa. El sistema reduce dramáticamente la carga en la BD RRHH al almacenar temporalmente los resultados de consultas frecuentes en memoria RAM.

**Beneficios obtenidos**:
- Reducción estimada de 90-99% de queries a BD RRHH para consultas repetidas
- Mejora de performance de 10-100x para consultas cacheadas
- TTL configurable (default: 5 minutos)
- Caché habilitado/deshabilitado desde variables de entorno
- Endpoints de administración para ADMIN y SUPERVISOR
- 18 tests unitarios + 11 tests de integración = 29 tests totales

## Endpoints Disponibles

### 1. POST /api/rrhh/cache/clear

**Descripción**: Limpia todo el caché de guardianes

**Autenticación**: JWT token requerido

**Autorización**: Solo ADMIN

**Request**:
```bash
POST /api/rrhh/cache/clear
Authorization: Bearer <token>
```

**Response** (200):
```json
{
  "message": "Caché limpiado exitosamente",
  "cacheEnabled": true,
  "statsBeforeClear": {
    "keys": 15,
    "hits": 320,
    "misses": 45
  }
}
```

**Errores**:
- 401: Token inválido o expirado
- 403: Usuario no es ADMIN
- 500: Error al limpiar caché

---

### 2. GET /api/rrhh/cache/stats

**Descripción**: Obtiene estadísticas del caché de guardianes

**Autenticación**: JWT token requerido

**Autorización**: ADMIN, SUPERVISOR

**Request**:
```bash
GET /api/rrhh/cache/stats
Authorization: Bearer <token>
```

**Response** (200):
```json
{
  "enabled": true,
  "keys": 15,
  "hits": 320,
  "misses": 45,
  "hitRate": 87.67,
  "memorySizeKB": 125.45,
  "ttlSeconds": 300
}
```

**Campos**:
- `enabled`: Caché habilitado/deshabilitado
- `keys`: Número de claves en caché
- `hits`: Aciertos (consultas desde caché)
- `misses`: Fallos (consultas a BD)
- `hitRate`: Porcentaje de aciertos (%)
- `memorySizeKB`: Memoria usada (KB)
- `ttlSeconds`: TTL configurado (segundos)

**Errores**:
- 401: Token inválido o expirado
- 403: Usuario no es ADMIN ni SUPERVISOR
- 500: Error al obtener estadísticas

## Estrategia de Cache Keys

### Formato de Claves

**Lista paginada**:
```
guardianes:active:page:{page}:size:{pageSize}:search:{search}
```

Ejemplos:
- `guardianes:active:page:1:size:10:search:` (página 1, sin búsqueda)
- `guardianes:active:page:1:size:20:search:juan` (página 1, búsqueda "juan")
- `guardianes:active:page:2:size:10:search:` (página 2, sin búsqueda)

**Guardián individual**:
```
guardian:{id}
```

Ejemplos:
- `guardian:1001`
- `guardian:1523`

### Invalidación

**Automática por TTL**:
- Default: 5 minutos (300 segundos)
- Configurable desde `CACHE_TTL_SECONDS`
- node-cache realiza limpieza automática cada 10 minutos

**Manual por ADMIN**:
- Endpoint: POST /api/rrhh/cache/clear
- Limpia TODAS las claves
- Retorna estadísticas antes de limpiar

**Futuro (no implementado)**:
- Webhook de BD RRHH para invalidación específica
- Invalidación por patrón de keys
- Cache warming al iniciar servidor

## Performance y Beneficios

### Métricas Esperadas

**Sin caché**:
- Query SQL: ~50-100ms
- Network + overhead: ~10-20ms
- **Total**: ~60-120ms por consulta

**Con caché (hit)**:
- Memory lookup: ~1-3ms
- Deserialización: ~1-2ms
- **Total**: ~2-5ms por consulta

**Mejora**: 10-60x más rápido

### Reducción de Carga en BD RRHH

**Escenario real**: Dashboard que consulta lista de guardianes cada 30 segundos

**Sin caché**:
- 120 queries/hora (1 cada 30s)
- 2,880 queries/día
- 86,400 queries/mes

**Con caché (TTL=5min)**:
- 12 queries/hora (1 cada 5min)
- 288 queries/día
- 8,640 queries/mes

**Ahorro**: 90% menos queries (77,760 queries/mes ahorradas)

### Memoria Utilizada

**Estimación por guardián**:
- Objeto JSON: ~500 bytes
- Overhead node-cache: ~100 bytes
- **Total**: ~600 bytes/guardián

**Caché completo** (515 guardianes):
- 515 × 600 bytes = 309 KB
- Con páginas múltiples: ~500 KB - 1 MB
- **Insignificante** para servidores modernos (GB de RAM)
