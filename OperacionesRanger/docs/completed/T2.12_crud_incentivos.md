## Decisiones Técnicas Tomadas

### 1. Estructura de BD Real vs. Especificación Inicial

**Decisión**: Usar estructura real de la tabla `incentivos_puesto` en lugar de la especificación inicial.

**Especificación inicial** (en tarea):
```
quincena_inicio, quincena_fin, monto, concepto, valor_hora (GENERATED), activo
```

**Estructura real de BD** (DESCRIBE):
```
anio, quincena, monto, valor_hora (GENERATED), fecha_inicio, fecha_fin, observaciones
```

**Justificación**:
- La estructura real es superior: `anio` + `quincena` + `fecha_inicio`/`fecha_fin` es más explícito
- `observaciones` es más flexible que `concepto`
- NO necesitamos campo `activo` - se puede eliminar el incentivo directamente (hard delete)
- `fecha_inicio`/`fecha_fin` permite periodos quincenales irregulares (ej: Feb 16-28)

### 2. Validación de Solapamiento con Query SQL

**Decisión**: Implementar detección de solapamiento mediante query SQL con 3 condiciones OR.

**Query implementada**:
```sql
WHERE puesto_id = ?
  AND (
    (fecha_inicio <= ? AND fecha_fin >= ?)  -- inicio nuevo dentro de existente
    OR (fecha_inicio <= ? AND fecha_fin >= ?)  -- fin nuevo dentro de existente
    OR (fecha_inicio >= ? AND fecha_fin <= ?)  -- existente dentro de nuevo
  )
```

**Justificación**:
- Cubre todos los escenarios de solapamiento
- Performance: query directa en BD es más eficiente que lógica en código
- Mantenibilidad: lógica centralizada en servicio

### 3. Hard Delete en lugar de Soft Delete

**Decisión**: Implementar hard delete (`DELETE`) para eliminar incentivos.

**Justificación**:
- La tabla NO tiene campo `activo` en BD
- Incentivos son datos temporales (periódicos)
- Si un incentivo ya no aplica, puede eliminarse completamente
- Simplifica la lógica: no necesitamos filtrar por `activo = true` en cada query

### 4. Ordenamiento de Rutas en Router

**Decisión**: Colocar `/quincena/:fecha` ANTES de `/:id` en el router.

**Justificación**:
- Express evalúa rutas en orden de definición
- Si `/:id` está primero, "quincena" se interpretaría como un ID
- Ordenamiento correcto evita conflictos de routing

### 5. Export de `db` para Compatibilidad

**Decisión**: Agregar export `db` en `database.ts` como wrapper de `getTurnosPool()`.

**Justificación**:
- Los tests y otros archivos usan `import { db } from '../config/database'`
- El patrón existente usa `getTurnosPool()` directamente
- El wrapper mantiene compatibilidad sin romper código existente

## Notas Adicionales

### Diferencia clave: Quincena vs. Periodo Quincenal

**Importante entender la diferencia**:
- **Quincena**: Periodo administrativo (1ra o 2da del mes)
- **Periodo quincenal**: Rango de fechas específico (`fecha_inicio` a `fecha_fin`)

En la implementación:
- `anio` + `quincena`: Identificadores administrativos
- `fecha_inicio` + `fecha_fin`: Periodo real de vigencia del incentivo

**Ejemplo**:
```
anio: 2026
quincena: 1
fecha_inicio: 2026-01-01
fecha_fin: 2026-01-15
```

Esto permite flexibilidad para periodos quincenales irregulares (ej: Febrero 2da quincena puede ser del 16 al 28).

---

### Valor hora: 360 horas por quincena

**Cálculo**:
- 15 días por quincena
- 24 horas por día
- 15 × 24 = 360 horas

**Uso en nómina**:
Cuando un guardián trabaja en un puesto con incentivo:
```
incentivo_guardián = horas_trabajadas × valor_hora
```

**Ejemplo**:
```
Incentivo: 36,000.00 pesos
Valor hora: 100.00 pesos/hora
Guardián trabaja 80 horas en el puesto
Incentivo del guardián: 80 × 100 = 8,000.00 pesos
```

3. **Capa de Servicios** (`services/incentivos.service.ts`)
   - Implementa lógica de negocio

**Beneficios**:
- Código testeable (cada capa se puede testear independientemente)
- Mantenible (cambios en BD no afectan routing)
- Escalable (fácil agregar nuevas validaciones o endpoints)
