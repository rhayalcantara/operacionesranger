### 3. ✅ Implementar PasswordService

**Archivo creado**: `backend/src/services/password.service.ts` (190 líneas)

**Funciones implementadas**:

#### 3.1. `hashPassword(password: string): Promise<string>`

**Propósito**: Genera hash bcrypt de una contraseña.

**Características**:
- Validación de longitud (8-100 caracteres)
- Usa bcrypt con rounds configurables (env.security.bcryptRounds)
- Salt aleatorio único por cada hash
- Operación asíncrona (no bloqueante)
- Manejo de errores con mensajes descriptivos

**Ejemplo de uso**:
```typescript
const hash = await hashPassword('MySecurePass123');
// Retorna: '$2a$10$N9qo8...' (60 caracteres)
```

**Validaciones**:
- Rechaza contraseña vacía
- Rechaza contraseña < 8 caracteres
- Rechaza contraseña > 100 caracteres

#### 3.2. `verifyPassword(password: string, hash: string): Promise<boolean>`

**Propósito**: Verifica si una contraseña coincide con un hash bcrypt.

**Características**:
- Comparación segura (timing-attack safe)
- Retorna boolean (nunca lanza error)
- Retorna false para hashes inválidos (no expone información)

**Ejemplo de uso**:
```typescript
const isValid = await verifyPassword('MySecurePass123', storedHash);
if (isValid) {
  console.log('Contraseña correcta');
} else {
  console.log('Contraseña incorrecta');
}
```

#### 3.3. `hashPasswordSync(password: string): string`

**Propósito**: Versión síncrona de hashPassword (solo para scripts/tests).

**⚠️ ADVERTENCIA**: Función BLOQUEANTE, no usar en rutas HTTP.

**Ejemplo de uso**:
```typescript
// En script de seed
const adminHash = hashPasswordSync('Admin123!');
db.execute('INSERT INTO sys_usuarios ...', [adminHash]);
```

**Validaciones**:
- Mismas validaciones que hashPassword async
- Propaga errores de validación

### 4. ✅ Implementar JWTService

**Archivo creado**: `backend/src/services/jwt.service.ts` (260 líneas)

**Funciones implementadas**:

#### 4.1. `generateAccessToken(payload): string`

**Propósito**: Genera access token JWT de corta duración (15 minutos).

**Payload requerido**:
```typescript
{
  sub: number;      // ID del usuario
  username: string; // Nombre de usuario
  rol: UserRole;    // Rol (ADMIN | SUPERVISOR | CONSULTA)
}
```

**Características**:
- Expiración: 15 minutos (configurable)
- Secret: JWT_SECRET
- Algorithm: HS256
- Claims automáticos: iat, exp
- Validación de payload completa

**Ejemplo de uso**:
```typescript
const accessToken = generateAccessToken({
  sub: 123,
  username: 'supervisor1',
  rol: UserRole.SUPERVISOR,
});
```

#### 4.2. `verifyAccessToken(token: string): JWTPayload | null`

**Propósito**: Verifica y decodifica access token.

**Retorno**:
- `JWTPayload` si válido
- `null` si inválido, expirado, o malformado

**Características**:
- NO lanza errores (siempre retorna null en caso de fallo)
- Verifica firma con JWT_SECRET
- Verifica expiración
- Logging de errores para debugging

**Ejemplo de uso**:
```typescript
const payload = verifyAccessToken(req.headers.authorization);
if (payload) {
  req.user = payload;
  next();
} else {
  return res.status(401).json({ error: 'Token inválido' });
}
```

#### 4.3. `generateRefreshToken(): string`

**Propósito**: Genera refresh token JWT de larga duración (7 días).

**Características**:
- Expiración: 7 días (configurable)
- Secret: JWT_REFRESH_SECRET (diferente del access)
- Payload mínimo: `{ type: 'refresh' }`
- Debe almacenarse hasheado (SHA-256) en BD

**Ejemplo de uso**:
```typescript
const refreshToken = generateRefreshToken();
const tokenHash = crypto.createHash('sha256').update(refreshToken).digest('hex');
// Almacenar tokenHash en sys_refresh_tokens
```

#### 4.4. `verifyRefreshToken(token: string): boolean`

**Propósito**: Verifica refresh token (solo firma y expiración).

**Retorno**:
- `true` si válido
- `false` si inválido o expirado

**IMPORTANTE**: Solo valida firma y expiración. La validación completa requiere consultar BD para verificar revocación.

**Ejemplo de uso**:
```typescript
if (!verifyRefreshToken(refreshToken)) {
  return res.status(401).json({ error: 'Refresh token inválido' });
}

// Verificar en BD si está revocado
const tokenHash = crypto.createHash('sha256').update(refreshToken).digest('hex');
const tokenRecord = await db.query(
  'SELECT * FROM sys_refresh_tokens WHERE token_hash = ? AND revocado = FALSE',
  [tokenHash]
);
```

#### 4.5. `decodeTokenWithoutVerification(token: string): any | null`

**Propósito**: Decodifica token sin verificar firma (solo debugging).

**⚠️ ADVERTENCIA**: NO usar para autenticación, solo para logs/debugging.

**Ejemplo de uso**:
```typescript
// En log de auditoría
const decoded = decodeTokenWithoutVerification(token);
console.log('Token info:', { userId: decoded.sub, username: decoded.username });
```

## Decisiones Técnicas Tomadas

### 1. bcryptjs vs bcrypt nativo

**Decisión**: Usar `bcryptjs` (pure JavaScript)

**Razones**:
- No requiere compilación C++ (cross-platform)
- Funciona en Windows sin Visual Studio Build Tools
- Compatible con todos los ambientes Cloud (Heroku, AWS Lambda, etc.)
- Sin dependencias nativas
- Performance aceptable (~100-200ms por hash con 10 rounds)

**Trade-off**: bcrypt nativo es ~2x más rápido, pero la diferencia es imperceptible en login/registro de usuarios.

### 2. Secrets separados para access y refresh tokens

**Decisión**: JWT_SECRET y JWT_REFRESH_SECRET deben ser diferentes

**Razones**:
- Seguridad: Si un secret se compromete, el otro sigue seguro
- Permite rotación independiente de secrets
- Refresh tokens más sensibles (larga duración) tienen secret separado
- Cumple con mejores prácticas de seguridad JWT

**Implementación**: Validación en env.ts que verifica que los secrets sean diferentes.

### 3. Access token de 15 minutos (no 30 minutos)

**Decisión**: JWT_ACCESS_EXPIRES_IN default = 15m (no 30m como en ADR-002)

**Razones**:
- Mayor seguridad (ventana de ataque más corta)
- El refresh token permite renovar sin fricción para el usuario
- 15 minutos es tiempo razonable para una sesión activa
- Si el usuario está inactivo > 15min, debe re-autenticarse (buena práctica)

**Trade-off**: El frontend debe implementar refresh automático al detectar 401.

### 4. Validación de longitud mínima de secrets

**Decisión**: JWT_SECRET y JWT_REFRESH_SECRET deben tener mínimo 32 caracteres

**Razones**:
- 32 caracteres = 256 bits de entropía si son hex (128 bits si son alfanuméricos)
- Protege contra ataques de fuerza bruta
- Estándar de industria para secrets criptográficos
- Fácil de generar con `crypto.randomBytes(32).toString('hex')`

**Implementación**: Nueva función `validateSecretLength()` en env.ts.

### 5. verifyPassword no lanza errores

**Decisión**: `verifyPassword()` siempre retorna boolean, nunca lanza error

**Razones**:
- No exponer información sobre la validez del hash (información sensible)
- Simplifica manejo de errores en login (solo true/false)
- Evita revelar detalles sobre hash inválido a atacantes
- Logging interno de errores para debugging

**Implementación**: try/catch interno con console.error, retorna false en todos los casos de error.

## Problemas Encontrados y Soluciones

### Problema 1: Interface SecurityConfig tenía campos opcionales

**Descripción**: En `env.ts`, `SecurityConfig` tenía `jwtSecret?: string` (opcional).

**Impacto**: Medio - Permitía que el sistema arranque sin JWT_SECRET configurado.

**Solución**:
- Cambiar a `jwtSecret: string` (requerido)
- Agregar `getRequiredEnv()` para JWT_SECRET
- Validación temprana (fail-fast) si falta variable

**Resultado**: ✅ Sistema no arranca sin JWT_SECRET configurado correctamente

### Problema 2: No había validación de longitud de secrets

**Descripción**: No se validaba que los secrets tuvieran longitud mínima segura.

**Impacto**: Alto - Secrets cortos son vulnerables a fuerza bruta.

**Solución**:
- Crear función `validateSecretLength(key, value, minLength)`
- Validar JWT_SECRET >= 32 caracteres
- Validar JWT_REFRESH_SECRET >= 32 caracteres
- Mensaje de error con comando para generar secret seguro

**Resultado**: ✅ Secrets cortos son rechazados al iniciar el servidor

### Problema 3: No había validación de secrets diferentes

**Descripción**: JWT_SECRET y JWT_REFRESH_SECRET podrían ser iguales.

**Impacto**: Medio - Reduce seguridad del sistema de doble token.

**Solución**:
- Agregar validación en `loadEnvConfig()`
- Comparar ambos secrets y rechazar si son iguales
- Mensaje de error explicando por qué deben ser diferentes

**Resultado**: ✅ Sistema no arranca si access y refresh secrets son iguales

## Lecciones Aprendidas

### 1. Validación temprana de secrets

**Lección**: Validar secrets al inicio del servidor (env.ts) evita errores en runtime.

**Beneficio**:
- Fail-fast: Si falta configuración, el servidor no arranca
- Mensajes de error claros con soluciones
- Evita bugs difíciles de debuggear en producción

**Aplicación futura**: Aplicar mismo patrón para otras configuraciones críticas.

### 2. Separación de secrets para access y refresh tokens

**Lección**: Tener secrets separados mejora seguridad significativamente.

**Beneficio**:
- Permite rotación independiente
- Limita impacto de compromiso de un secret
- Cumple con mejores prácticas de seguridad

**Aplicación futura**: Siempre separar secrets de diferentes subsistemas.

### 3. Tests desde el inicio aceleran desarrollo

**Lección**: Escribir tests mientras desarrollas te fuerza a pensar en casos edge.

**Beneficio**:
- Detección temprana de bugs
- Código más robusto (validaciones completas)
- Confianza al refactorizar

**Aplicación futura**: TDD (Test-Driven Development) para funciones críticas.
