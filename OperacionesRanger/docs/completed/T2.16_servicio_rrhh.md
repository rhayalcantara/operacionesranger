## Decisiones Técnicas Tomadas

### Decisión 1: Usar pool de conexión separado para BD RRHH

**Justificación**:
- Pool ya existente en `database.ts` configurado específicamente para BD RRHH
- Pool con límite de 5 conexiones (apropiado para READ-ONLY)
- Separación de responsabilidades (turnos vs RRHH)
- Facilita monitoreo y troubleshooting

**Implementación**:
```typescript
import { getRRHHPool } from '../config/database';
const pool = getRRHHPool();
```

---

### Decisión 2: Transformar registros de BD a interfaces TypeScript

**Justificación**:
- Fechas vienen como strings desde MySQL, necesitan conversión a Date objects
- Campo `nombre_completo` se computa en query pero también se puede generar
- Campos nullables requieren manejo apropiado
- Separación entre `GuardianDB` (raw) y `Guardian` (transformado)

**Implementación**:
```typescript
export function transformGuardian(dbRecord: GuardianDB): Guardian {
  return {
    ...dbRecord,
    nombre_completo: `${dbRecord.nombres} ${dbRecord.apellidos}`,
    fecha_ingreso: typeof dbRecord.fecha_ingreso === 'string'
      ? new Date(dbRecord.fecha_ingreso)
      : dbRecord.fecha_ingreso,
    // ... más transformaciones
  };
}
```

---

### Decisión 3: Paginación obligatoria con límite máximo

**Justificación**:
- BD RRHH tiene ~515 guardianes activos según T002
- Retornar todos sin paginación sería ineficiente
- Límite de pageSize=100 previene queries muy pesadas

**Implementación**:
```typescript
const pageSize = Math.min(
  GUARDIAN_CONSTANTS.MAX_PAGE_SIZE, // 100
  Math.max(1, filters.pageSize || GUARDIAN_CONSTANTS.DEFAULT_PAGE_SIZE) // 10
);
```

---

### Decisión 4: Manejo específico de errores de BD RRHH

**Justificación**:
- BD RRHH es externa y puede estar no disponible
- Errores deben ser claros para debugging
- Códigos HTTP deben reflejar tipo de error (503, 504 vs 500)

**Implementación**:
```typescript
catch (error) {
  if (error.message.includes('ECONNREFUSED')) {
    throw new Error('Base de datos RRHH no disponible...');
  }
  if (error.message.includes('ETIMEDOUT')) {
    throw new Error('Timeout al consultar BD RRHH...');
  }
  throw new Error(`Error al consultar: ${error.message}`);
}
```

---

### Decisión 5: Todos los roles pueden acceder a endpoints RRHH

**Justificación**:
- Requisito explícito: ADMIN, SUPERVISOR, CONSULTA pueden consultar guardianes
- Consultar guardianes es necesario para todos los usuarios del sistema
- No hay datos sensibles expuestos (salario_base, cuenta_bancaria excluidos)

**Implementación**:
```typescript
router.use(requireRole(UserRole.ADMIN, UserRole.SUPERVISOR, UserRole.CONSULTA));
```

---

### Decisión 6: Límite de 20 resultados en búsqueda rápida

**Justificación**:
- Búsqueda rápida es para autocomplete/dropdown
- 20 resultados es suficiente para mostrar opciones relevantes
- Mejora performance evitando retornar cientos de resultados

**Implementación**:
```typescript

// ... en query
LIMIT ?
// ... params
[..., GUARDIAN_CONSTANTS.SEARCH_LIMIT]
```

### Queries SQL Optimizadas

**Query principal** (getGuardianes):
```sql
SELECT
  e.id_empleado,
  e.codigo_empleado,
  e.cedula_empleado,
  e.nombres,
  e.apellidos,
  CONCAT(e.nombres, ' ', e.apellidos) AS nombre_completo,
  e.email,
  e.telefono,
  e.fecha_ingreso,
  e.id_puesto,
  e.status,
  e.created_at,
  e.updated_at
FROM rh_empleado e
WHERE e.id_puesto = 97
  AND e.status = 1
  AND (e.nombres LIKE ? OR e.apellidos LIKE ? OR e.cedula_empleado LIKE ?)
ORDER BY e.apellidos ASC, e.nombres ASC
LIMIT ? OFFSET ?
```

**Índices utilizados** (existentes en BD RRHH):
- `idx_puesto` en `id_puesto` - Optimiza filtro principal
- `idx_status` en `status` - Optimiza filtro de activos
- `PRIMARY KEY` en `id_empleado` - Optimiza búsqueda por ID
