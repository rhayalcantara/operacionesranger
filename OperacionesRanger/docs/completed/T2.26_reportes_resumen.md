## Resumen

Implementación exitosa de 3 endpoints REST para generar reportes de resumen en formato JSON de turnos de guardianes. Los endpoints proporcionan vistas estadísticas agregadas para dashboards y análisis, complementando el reporte CSV de nómina (T2.23).

**Endpoints implementados**:
1. `GET /api/reportes/resumen-quincena` - Resumen agregado del período
2. `GET /api/reportes/resumen-por-guardian` - Estadísticas por empleado (paginado)
3. `GET /api/reportes/resumen-por-puesto` - Estadísticas por puesto (paginado)

Todos los endpoints retornan **JSON** (no CSV), son accesibles por **todos los usuarios autenticados** (ADMIN, SUPERVISOR, CONSULTA), e incluyen **validación robusta** con Zod schemas y **queries SQL optimizadas** con GROUP BY y JOINs.

#### 1.1. `getResumenQuincena(fecha_inicio, fecha_fin): Promise<ResumenQuincenaDTO>`

Genera resumen estadístico agregado de todos los turnos en el rango de fechas.

**Características**:
- **Query SQL optimizada** con 3 subconsultas:
  1. Estadísticas generales (COUNT, SUM, COUNT DISTINCT)
  2. Distribución por tipo de turno (GROUP BY tipo_turno)
  3. Cálculo de incentivos (JOINs con incentivos_puesto)
- **Validaciones**:
  - `fecha_inicio <= fecha_fin`
  - Rango máximo: 93 días (trimestre)
- **Campos calculados**:
  - `total_turnos`, `total_horas_normales`, `total_horas_extras`
  - `total_guardianes` (COUNT DISTINCT empleado_id)
  - `turnos_por_tipo`: `{ DIURNO: X, NOCTURNO: Y }`
  - `turnos_feriados` (SUM con CASE)
  - `total_incentivos` (cálculo con valor_hora)
- **Manejo de resultado vacío**: Retorna estructura con zeros
- **Logging**: Operaciones importantes logueadas

**Complejidad de queries**:
- Query 1: `COUNT(*), SUM(horas_*), COUNT(DISTINCT empleado_id)` con WHERE fecha BETWEEN
- Query 2: `GROUP BY tipo_turno` para distribución
- Query 3: `LEFT JOINs` con puestos e incentivos_puesto, filtrado por quincena

**Performance**: Queries optimizadas usando índices en `fecha`, `empleado_id`, `puesto_id`.

#### 1.2. `getResumenPorGuardian(filtros, paginacion): Promise<PaginatedResumenResponse<ResumenGuardianDTO>>`

Genera resumen estadístico por empleado (guardián) con paginación.

**Características**:
- **Filtros opcionales**:
  - `empleado_id` (opcional): Filtrar por un guardián específico
  - `fecha_inicio`, `fecha_fin` (requeridos): Rango de fechas
- **Paginación configurable**:
  - `page` (default: 1, min: 1)
  - `pageSize` (default: 10, min: 1, max: 100)
- **Query SQL** con doble conexión:
  1. Consulta a BD Turnos (agregaciones por empleado_id)
  2. Consulta a BD RRHH (datos del empleado: nombre, cédula)
- **Agregaciones por empleado**:
  - `total_turnos`, `total_horas_normales`, `total_horas_extras`
  - `turnos_diurnos`, `turnos_nocturnos` (SUM con CASE)
  - `turnos_feriados` (SUM con CASE)
  - `total_incentivos` (JOINs con incentivos_puesto)
- **Ordenamiento**: `ORDER BY total_turnos DESC` (más activos primero)
- **Integración BD RRHH**:
  - Query a `rh_empleado` con `IN (empleadosIds)`
  - Mapa de empleados para acceso rápido (O(1))
  - Manejo de empleados no encontrados: "Desconocido", "N/A"

**Complejidad de queries**:
- Count query: `COUNT(DISTINCT t.empleado_id)` con WHERE dinámico
- Data query: `GROUP BY t.empleado_id` con `LEFT JOINs` a puestos e incentivos
- RRHH query: `SELECT ... FROM rh_empleado WHERE id_empleado IN (...)`

**Performance**:
- Paginación con `LIMIT ? OFFSET ?`
- Índices usados: `turnos(fecha, empleado_id)`, `incentivos_puesto(puesto_id, quincena_inicio, quincena_fin)`

#### 1.3. `getResumenPorPuesto(filtros, paginacion): Promise<PaginatedResumenResponse<ResumenPuestoDTO>>`

Genera resumen estadístico por puesto de trabajo con filtros jerárquicos.

**Características**:

### Problema 3: Cálculo de incentivos con múltiples JOINs
**Descripción**: El cálculo de `total_incentivos` requiere un JOIN con `incentivos_puesto` que tiene columna generada `valor_hora` (monto / 360). El JOIN debe considerar que un turno solo tiene incentivo si su fecha está dentro del rango de quincena del incentivo.

**Solución**: Implementé LEFT JOIN con condiciones compuestas:
```sql
LEFT JOIN incentivos_puesto ip ON p.id = ip.puesto_id
  AND t.fecha BETWEEN ip.quincena_inicio AND ip.quincena_fin
  AND ip.activo = 1
```
Luego calculé el incentivo del turno como:
```sql
(t.horas_normales + t.horas_extras) * ip.valor_hora
```

**Tiempo invertido**: 20 minutos

## Decisiones Técnicas Tomadas

### Decisión 1: Doble conexión a BD para resumen por guardián
**Justificación**: El resumen por guardián requiere datos de la tabla `turnos` (BD Turnos) Y datos de `rh_empleado` (BD RRHH). En lugar de hacer un JOIN cross-database (complejo y no portable), implementé:
1. Query a BD Turnos para agregaciones (turnos, horas, etc.)
2. Query a BD RRHH con `IN (empleadosIds)` para datos del empleado
3. Mapa en memoria para vincular datos (O(1) lookup)

**Beneficio**: Queries simples, portable, fácil de entender y mantener.

---

### Decisión 2: Queries SQL directas (no stored procedures)
**Justificación**: Los stored procedures existentes (`sp_registrar_turno`, `sp_generar_reporte_nomina`) son para operaciones críticas que modifican datos o generan reportes CSV. Los reportes de resumen son **consultas de solo lectura** con GROUP BY y filtros dinámicos, más apropiadas para SQL directo en el servicio.

**Beneficio**: Flexibilidad para filtros opcionales sin modificar la BD.

---

### Decisión 3: Límite de 93 días para resumen-quincena
**Justificación**: Rango máximo de 93 días (trimestre) para prevenir queries muy pesadas. El límite es razonable para reportes de resumen (normalmente se consultan quincenas o meses).

**Beneficio**: Protección contra queries lentas, optimización de performance.

---

### Decisión 4: Paginación obligatoria en resumen-por-guardian y resumen-por-puesto
**Justificación**:
- **Resumen-quincena**: Retorna UN solo objeto (sin paginación necesaria)
- **Resumen-por-guardian**: Puede retornar cientos de guardianes (paginación necesaria)
- **Resumen-por-puesto**: Puede retornar cientos de puestos (paginación necesaria)

**Beneficio**: Respuestas rápidas incluso con grandes volúmenes de datos.

---

### Decisión 5: Ordenamiento por total_turnos DESC
**Justificación**: Los reportes de resumen por guardián y por puesto ordenan por `total_turnos DESC` para mostrar primero a los más activos/utilizados. Este ordenamiento es más útil para análisis que ordenamiento alfabético.

**Beneficio**: UX mejorada, información más relevante primero.
