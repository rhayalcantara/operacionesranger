### 1. Migración SQL

**Archivo**: `backend/database/migrations/003_sys_reportes_generados.sql` (43 líneas)

**Tabla creada**: `sys_reportes_generados`

**Esquema**:
```sql
CREATE TABLE sys_reportes_generados (
    id INT AUTO_INCREMENT PRIMARY KEY,
    user_id INT NOT NULL,
    fecha_inicio DATE NOT NULL,
    fecha_fin DATE NOT NULL,
    cantidad_turnos INT NOT NULL,
    fecha_generacion DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    nomina_id INT NULL,
    nombre_archivo VARCHAR(100) NOT NULL,

    CONSTRAINT fk_reportes_user FOREIGN KEY (user_id)
        REFERENCES sys_usuarios(id),

    INDEX idx_user_fecha (user_id, fecha_generacion),
    INDEX idx_fecha_generacion (fecha_generacion),
    INDEX idx_nomina (nomina_id)
) ENGINE=InnoDB;
```

**Campos clave**:
- `user_id`: Usuario que generó el reporte (FK a `sys_usuarios`)
- `cantidad_turnos`: Cantidad de turnos incluidos en el reporte
- `fecha_generacion`: Timestamp de cuando se generó (auto)
- `nomina_id`: ID de nómina (NULL hasta que se procese, luego se actualiza)
- `nombre_archivo`: Nombre del CSV generado (formato: `nomina_YYYYMMDD_YYYYMMDD.csv`)

**Índices**:
- `idx_user_fecha`: Optimiza consultas por usuario y fecha
- `idx_fecha_generacion`: Optimiza ordenamiento DESC
- `idx_nomina`: Optimiza búsquedas por nómina procesada

## Decisiones Técnicas Tomadas

### 1. Guardar parámetros, no contenido CSV

**Decisión**: Guardar solo `fecha_inicio`, `fecha_fin`, `cantidad_turnos` en lugar del contenido completo del CSV.

**Razón**:
- El CSV puede ser muy grande (miles de registros)
- Almacenar CSV completo ocuparía mucho espacio en BD
- Los datos del CSV pueden cambiar si se modifican turnos
- Regenerar CSV garantiza datos actualizados

**Trade-off aceptado**: El CSV re-generado puede ser diferente al original si se modificaron turnos. Esto es útil, no un problema.

### 2. Actualizar solo último reporte en marcar-procesados

**Decisión**: Al marcar como procesados, solo actualizar el registro MÁS RECIENTE del historial para ese rango.

**Razón**:
- Puede haber múltiples reportes para el mismo rango (regeneraciones)
- Solo el último reporte generado es el que se procesó
- SQL: `ORDER BY fecha_generacion DESC LIMIT 1`

**Alternativa rechazada**: Actualizar TODOS los registros con ese rango → incorrecto, contamina historial.

### 3. user_id en re-descarga es el usuario actual

**Decisión**: Al re-descargar un reporte, el `user_id` usado en la regeneración es el del usuario ACTUAL, no el original.

**Razón**:
- Auditoría: saber quién descargó el reporte regenerado
- El usuario actual puede ser diferente al que generó originalmente
- Cada regeneración crea un NUEVO registro en historial

**Comportamiento**: Un reporte puede tener múltiples "descargas" en el historial.

### 4. Orden de rutas: /historial antes de /:id/descargar

**Decisión**: Registrar ruta `/historial` ANTES de `/:id/descargar` en Express router.

**Razón técnica**: Express evalúa rutas en orden. Si `/:id/descargar` está primero, Express interpretaría `/historial` como un ID, causando error 404 o 400.

**Implementación**:
```typescript
router.get('/historial', ...);      // PRIMERO (ruta estática)
router.get('/:id/descargar', ...);  // SEGUNDO (ruta dinámica)
```

### 5. Manejo de errores no críticos

**Decisión**: Si falla el guardado en historial, logear error pero NO fallar la generación del CSV.

**Razón**:
- Guardado de historial es útil pero no crítico
- Si falla, el usuario aún puede descargar su CSV
- Error se loguea para debugging

**Implementación**:
```typescript
try {
  await guardarHistorialReporte(...);
} catch (historialError) {
  console.error('Error al guardar historial (no crítico):', historialError);
  // NO throw, continuar
}
```

### Performance

**Impacto en generación de reportes**: Mínimo
- INSERT adicional en `sys_reportes_generados`: ~10ms
- No afecta generación del CSV (asíncrono)
- Error en historial NO bloquea descarga

**Impacto en consulta de historial**: Optimizado
- Índices en `fecha_generacion`, `user_id`, `nomina_id`
- JOIN con `sys_usuarios` es rápido (PK)
- Paginación obligatoria (max 100 registros)

### Seguridad

**Permisos**:
- GET /historial: ADMIN, SUPERVISOR, CONSULTA (todos pueden ver)
- GET /:id/descargar: ADMIN, SUPERVISOR, CONSULTA (todos pueden descargar)
- Todos los endpoints protegidos por `authMiddleware`

**Auditoría**:
- Cada descarga regenera y crea nuevo registro en historial

## Comandos de Prueba

### 1. Generar reporte y verificar historial

```bash
# Generar reporte
curl -X POST http://localhost:3000/api/reportes/nomina \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"fecha_inicio":"2026-01-01","fecha_fin":"2026-01-15"}' \
  --output reporte.csv

# Ver historial
curl -X GET "http://localhost:3000/api/reportes/historial?page=1&pageSize=10" \
  -H "Authorization: Bearer <token>"
```

### 2. Marcar como procesados y verificar actualización

```bash
# Marcar como procesados
curl -X POST http://localhost:3000/api/reportes/marcar-procesados \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "fecha_inicio":"2026-01-01",
    "fecha_fin":"2026-01-15",
    "nomina_id":125
  }'

# Ver historial actualizado (nomina_id debe estar vinculado)
curl -X GET "http://localhost:3000/api/reportes/historial?page=1&pageSize=10" \
  -H "Authorization: Bearer <token>"
```

### 3. Re-descargar reporte histórico

```bash
# Obtener ID del último reporte
curl -X GET "http://localhost:3000/api/reportes/historial?page=1&pageSize=1" \
  -H "Authorization: Bearer <token>"
# Supongamos que retorna ID = 5

# Re-descargar ese reporte
curl -X GET http://localhost:3000/api/reportes/5/descargar \
  -H "Authorization: Bearer <token>" \
  --output reporte_regenerado.csv
```

### 4. Verificar en MySQL

```sql
-- Ver historial completo
SELECT
  h.id,
  u.username,
  h.fecha_inicio,
  h.fecha_fin,
  h.cantidad_turnos,
  h.fecha_generacion,
  h.nomina_id,
  h.nombre_archivo
FROM sys_reportes_generados h
INNER JOIN sys_usuarios u ON h.user_id = u.id_usuario
ORDER BY h.fecha_generacion DESC;

-- Ver reportes NO procesados (nomina_id NULL)
SELECT * FROM sys_reportes_generados WHERE nomina_id IS NULL;

-- Ver reportes procesados para nómina específica
SELECT * FROM sys_reportes_generados WHERE nomina_id = 125;
```
