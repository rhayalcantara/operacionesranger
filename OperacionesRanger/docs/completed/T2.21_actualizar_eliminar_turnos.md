```typescript
async function verificarTurnoNoProcesado(id: number): Promise<void> {
  const pool = getTurnosPool();

  const [rows] = await pool.execute<RowDataPacket[]>(
    'SELECT procesado_nomina FROM turnos WHERE id = ? LIMIT 1',
    [id]
  );

  if (rows.length === 0) {
    throw new TurnoNoExisteError(id);
  }

  const turno = rows[0];
  if (turno.procesado_nomina) {
    throw new TurnoProcesadoError(id);
  }
}
```

## Decisiones Técnicas Tomadas

### Decisión 1: Estrategia UPDATE = DELETE + INSERT

**Justificación**:
- Re-ejecuta validaciones completas del SP
- Recalcula campos automáticos (tipo_turno, es_feriado)
- Reutiliza lógica existente en vez de duplicar
- Garantiza consistencia con INSERT inicial

**Desventaja aceptada**: El ID del turno cambia
**Mitigación**: Retornar turno completo con nuevo ID en response

---

### Decisión 2: Uso de transacciones en actualizarTurno

**Justificación**:
- Operación DELETE + INSERT debe ser atómica
- Rollback automático si SP falla
- Previene estado inconsistente

**Implementación**:
```typescript
const connection = await pool.getConnection();
await connection.beginTransaction();

try {
  // DELETE + INSERT via SP
  await connection.commit();
} catch (error) {
  await connection.rollback();
  throw error;
} finally {
  connection.release();
}
```

---

### Decisión 3: Permisos diferenciados PUT vs DELETE

**PUT /api/turnos/:id**:
- ADMIN: ✅ Puede actualizar
- SUPERVISOR: ✅ Puede actualizar
- CONSULTA: ❌ No puede actualizar

**DELETE /api/turnos/:id**:
- ADMIN: ✅ Puede eliminar
- SUPERVISOR: ❌ NO puede eliminar
- CONSULTA: ❌ No puede eliminar

**Justificación**: Eliminar es más peligroso que actualizar (pérdida irreversible de datos). Solo ADMIN debe tener este poder.

---

### Decisión 4: Campos NO modificables vía PUT

**Campos bloqueados**:
- empleado_id: Cambiaría quién trabajó el turno
- puesto_id: Cambiaría dónde se trabajó
- fecha: Cambiaría el día del turno

**Razón**: Modificar estos campos cambiaría la naturaleza fundamental del turno

**Solución para usuario**: Si necesita cambiar estos campos, usar DELETE + POST manual

---

### Decisión 5: Validación procesado_nomina en múltiples capas

**Capa 1 - Helper privado**: verificarTurnoNoProcesado()
- Lanza TurnoProcesadoError si procesado_nomina = TRUE

**Capa 2 - Service**: actualizarTurno(), eliminarTurno()
- Llaman a helper antes de cualquier operación

**Capa 3 - Controller**: Mapeo a 403 Forbidden
- Error claro al usuario

**Justificación**: Inmutabilidad de turnos procesados es CRÍTICA para integridad con sistema de nómina

### Inmutabilidad de Turnos Procesados

**Regla de oro**: Un turno con procesado_nomina = TRUE es INMUTABLE

**Razón**:
- El turno ya fue exportado al sistema de nómina
- La nómina ya fue generada y posiblemente pagada
- Modificarlo causaría inconsistencias entre sistemas
- Podría afectar cálculos salariales, impuestos, reportes

**Enforcement**:
- Validación en helper verificarTurnoNoProcesado()
- Error 403 Forbidden si se intenta modificar
- Mensaje claro: "El turno X ya fue procesado en nómina y no puede ser modificado"

**Flujo de corrección**:
Si un turno procesado tiene error:
1. NO modificar el turno existente
2. Registrar nota en observaciones del siguiente turno
3. Crear ajuste manual en sistema de nómina
4. Documentar discrepancia para auditoría
