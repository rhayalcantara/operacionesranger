## Decisiones Técnicas Tomadas

### 1. Uso de Enums vs String Literal Types

**Decisión**: Se usaron **TypeScript enums** para `UserRole` y `AuthEvent` (ya implementado en auth.model.ts existente).

**Razón**:
- Enums generan valores en JavaScript (útil para validación en runtime)
- Mejor para logging y debugging (muestra el nombre del enum)
- Compatible con Zod mediante `z.enum(['ADMIN', 'SUPERVISOR', 'CONSULTA'])`

**Alternativa descartada**: String literal types (`type UserRole = 'ADMIN' | 'SUPERVISOR' | 'CONSULTA'`)
- No genera valores en runtime
- Menos útil para validación

### 2. Password Validation Requirements

**Decisión**: Password debe tener **al menos 1 mayúscula, 1 minúscula, 1 número** (NO se requieren caracteres especiales).

**Razón**:
- Balance entre seguridad y usabilidad
- Caracteres especiales pueden dificultar el uso (especialmente en teclados móviles)
- Requisito de 8 caracteres mínimo + complejidad ya provee seguridad adecuada
- Según ADR-002 sección de seguridad

**Configuración**:
```typescript
PASSWORD_REQUIREMENTS.REGEX = /^(?=.*[a-z])(?=.*[A-Z])(?=.*\d).+$/
```

### 3. Estructura de Schemas de Validación

**Decisión**: Crear **building blocks reutilizables** (usernameSchema, passwordSchema, emailSchema) y componer schemas complejos a partir de ellos.

**Razón**:
- DRY (Don't Repeat Yourself)
- Consistencia en validaciones
- Fácil mantenimiento (cambiar en un solo lugar)
- Mejor legibilidad

**Ejemplo**:
```typescript
const createUserSchema = z.object({
  username: usernameSchema,      // Reutilizado
  password: passwordSchema,      // Reutilizado
  email: emailSchema,            // Reutilizado
  nombre_completo: nombreCompletoSchema,
  rol: rolSchema
});
```

### 4. Self-Referencing Foreign Keys

**Decisión**: Usar **ON DELETE SET NULL** para foreign keys `created_by` y `modified_by` en `sys_usuarios`.

**Razón**:
- Permite eliminar usuarios sin romper referencias circulares
- Primer usuario (admin seed) tiene created_by = NULL
- Preserva información de auditoría (aunque sea NULL)
- Alternativa CASCADE causaría eliminar todos los usuarios creados por el eliminado

### 5. Límite de Refresh Tokens

**Decisión**: Máximo **5 refresh tokens activos por usuario** (controlado por trigger).

**Razón**:
- Evita acumulación ilimitada de tokens
- Permite múltiples dispositivos (móvil + desktop + tablet)
- No tan restrictivo como 1 token (cerraría sesiones al hacer login en otro dispositivo)
- Trigger automáticamente revoca el más antiguo si se excede el límite
