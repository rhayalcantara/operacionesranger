### 3. `frontend/src/app/core/guards/auth.guard.ts` (105 líneas)
**Descripción**: Guard funcional para proteger rutas que requieren autenticación

**Lógica**:
1. Verificar si usuario está autenticado (`isAuthenticated()`)
2. Si SÍ → permitir acceso (return true)
3. Si NO:
   - Verificar si hay refresh token
   - Intentar auto-refresh del access token
   - Si refresh exitoso → permitir acceso
   - Si falla → redirigir a /login con returnUrl

**Características**:
- Functional guard (Angular 20 style)
- Auto-refresh automático de tokens expirados
- returnUrl en queryParams para redirigir después de login
- Versión class-based comentada como alternativa

**Uso en routing**:
```typescript
import { authGuard } from './core/guards/auth.guard';

const routes: Routes = [
  {
    path: 'dashboard',
    component: DashboardComponent,
    canActivate: [authGuard]
  }
];
```

### 5. `frontend/src/app/core/interceptors/auth.interceptor.ts` (190 líneas)
**Descripción**: Interceptor HTTP para agregar tokens y manejar auto-refresh

**Funcionalidad**:

**Request Interceptor**:
- Agrega header `Authorization: Bearer {token}` a todas las requests
- NO agrega token a endpoints de autenticación (/api/auth/login, /api/auth/refresh)
- Clona request y modifica headers

**Response Interceptor (401 Unauthorized)**:
- Intercepta errores 401
- Verifica que no sea el endpoint de refresh (evitar loop)
- Intenta refresh token automáticamente
- Si refresh exitoso:
  - Actualiza access token en localStorage
  - Retry request original con nuevo token
- Si refresh falla:
  - Hace logout
  - Redirige a /login

**Características**:
- Functional interceptor (Angular 20 style)
- Prevención de refresh loops
- Retry automático de requests fallidos
- Logs detallados para debugging
- Versión class-based comentada con BehaviorSubject para manejar requests concurrentes

**Uso en app.config.ts**:
```typescript
import { provideHttpClient, withInterceptors } from '@angular/common/http';
import { authInterceptor } from './core/interceptors/auth.interceptor';

export const appConfig: ApplicationConfig = {
  providers: [
    provideHttpClient(
      withInterceptors([authInterceptor])
    )
  ]
};
```

## Ejemplos de Uso

### 1. Login desde componente

```typescript
import { Component } from '@angular/core';
import { Router } from '@angular/router';
import { AuthService } from '../core/services/auth.service';

@Component({
  selector: 'app-login',
  template: `
    <form (ngSubmit)="onSubmit()">
      <input [(ngModel)]="username" placeholder="Username">
      <input [(ngModel)]="password" type="password" placeholder="Password">
      <button type="submit">Login</button>
    </form>
  `
})
export class LoginComponent {
  username = '';
  password = '';

  constructor(
    private authService: AuthService,
    private router: Router
  ) {}

  onSubmit() {
    this.authService.login({ username: this.username, password: this.password })
      .subscribe({
        next: (response) => {
          console.log('Login successful:', response.user);
          this.router.navigate(['/dashboard']);
        },
        error: (error) => {
          console.error('Login failed:', error);
          alert('Login failed: ' + error.message);
        }
      });
  }
}
```

## Decisiones Técnicas Tomadas

### 1. Functional Guards e Interceptors (Angular 20 style)
**Decisión**: Usar functional guards (`CanActivateFn`) e interceptors (`HttpInterceptorFn`) en lugar de class-based.

**Justificación**:
- Angular 20 recomienda functional approach para mejor tree-shaking
- Más ligero y fácil de testear
- Mejor integración con standalone components
- Versiones class-based incluidas como comentarios para referencia

---

### 2. localStorage para tokens
**Decisión**: Usar `localStorage` para almacenar access token, refresh token y user data.

**Justificación**:
- Fácil de implementar
- Persiste entre sesiones del navegador
- Compatible con SPA (Single Page Applications)

**Riesgo**: Vulnerable a ataques XSS (Cross-Site Scripting)

**Mitigación futura**: Considerar httpOnly cookies para mayor seguridad (requiere cambio en backend).

---

### 3. BehaviorSubject para estado de autenticación
**Decisión**: Usar `BehaviorSubject<AuthState>` para estado reactivo.

**Justificación**:
- Permite a componentes suscribirse a cambios de autenticación
- Emite último valor inmediatamente al suscribirse
- Perfecto para header/navbar que necesitan mostrar usuario actual

---

### 4. Auto-refresh en AuthGuard y AuthInterceptor
**Decisión**: Implementar auto-refresh de tokens en ambos lugares.

**Justificación**:
- **AuthGuard**: Refresh preventivo al navegar a ruta protegida
- **AuthInterceptor**: Refresh reactivo cuando request falla con 401

Esta redundancia asegura mejor UX (menos interrupciones).

---

### 5. Prevención de refresh loops
**Decisión**: Flag `isRefreshing` en AuthService + verificación de endpoint en AuthInterceptor.

**Justificación**:
- Evita múltiples requests de refresh simultáneos
- Previene loops infinitos si refresh token también está expirado
- Si refresh falla, hace logout inmediato

---

### 6. Formateo de errores por status code
**Decisión**: ErrorInterceptor formatea mensajes según status code específico.

**Justificación**:
- Mensajes más amigables para usuarios
- Manejo especial de errores de validación (400, 422)
- Logs detallados en development, logs básicos en production

---

### 7. Logs detallados en guards e interceptors
**Decisión**: Incluir `console.log` y `console.error` en todos los flujos.

**Justificación**:
- Facilita debugging durante desarrollo
- Ayuda a entender flujo de autenticación
- En producción, considerar remover o usar servicio de logging externo
